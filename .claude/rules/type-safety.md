# Type Safety

型は契約。コンパイラの型エラーは「このメソッド・型は実在しない / 形が違う」
という実バグの可能性を指している。**消すのではなく、診断して直す**こと。

## 不慣れな API を使う前に

**実型を先に確認する。推測で書かない。**

確認手段 (信頼できる順):

1. ローカル型定義 — IDE の go-to-definition / `gh api` で上流ソース / NuGet/npm パッケージの中身
2. 公式ドキュメント (Context7 MCP)
3. リポジトリ内の既存呼び出し箇所
4. Web 検索 (最後の手段)

リファレンス実装をなぞるときも**注意深く読むこと**。
コメントアウトされた行 + 別実装の hack (例: `// var x = real_api(); var x = workaround_x;`) は
「動かなかったから諦めた」load-bearing workaround であって、消していい dead code ではない。

## 型エラーが出たとき

**suppress するのは原則 NG**。下のパターンは「コンパイラに黙ってもらう」だけで、
runtime に問題を押し付けている:

| 言語        | 避ける                                                            |
| ----------- | ----------------------------------------------------------------- |
| C#          | `dynamic`、`(object)` キャスト、当てずっぽうの null-forgiving `!` |
| TypeScript  | `any`、`as unknown as T`、`@ts-ignore`、`@ts-expect-error`        |
| Rust        | borrow check 回避の `unsafe`、信用できない `Option` の `unwrap()` |
| Java/Kotlin | 生 raw type、`!!` (Kotlin)、`@SuppressWarnings("unchecked")`      |
| 共通        | 戻り値を即キャストし直す chain                                    |

これらに手が伸びたら**一旦停止**して、実型を調べる。

## "型を捨てるコスト" は runtime のコストに比例する

runtime 失敗のフィードバックが遅いほど、型を尊重しなければならない:

| 検証ループ                            | 型ゆるさの許容度         |
| ------------------------------------- | ------------------------ |
| Hot reload (秒単位)                   | プロトタイピング中は多少 |
| ユニットテスト (秒〜分)               | 注意                     |
| ビルド + 起動 + 手動 UI 確認 (分単位) | 型は安全装置として使う   |
| クロスマシン / クロスプロセス自動化   | 型は基幹インフラ         |

「Windows + GUI アプリを遠隔操作する CLI、検証には deploy + 起動が必要」のような
高コスト環境で `dynamic` を使うのは**最悪の選択**。最初の `dynamic` のせいで
1 周回すたびに数分〜数十分溶ける。

## アンチパターン (実例)

- API を記憶頼りで書く → 出た型エラーを `dynamic`/`any` で消す。
  → **元の推測が間違い。型を調べ直すのが正解**
- 戻り値型が分からないから `dynamic` で受ける + 全部の chain を `dynamic`化
  → 1 ステップずつ型を辿って、本当の型名を特定する
- ローカル変数は `var` で逃げて OK だが、**ヘルパー関数に切り出した瞬間に型を要求される**。
  切り出すなら型を知っている必要がある
- "とりあえずビルドを通したい" だけのキャスト。runtime で `RuntimeBinderException` /
  `TypeError` が出る形に変えただけで、本質的に直っていない

## 振る舞いとしての要点

1. **不明な API は呼ぶ前に調べる**、書いた後ではなく
2. **型エラーは原因を理解してから直す**、消しに行かない
3. **`dynamic` / `any` を入れるときは正当化を書く** (なぜ静的に解けないか、なぜそれで安全か)
4. **CI でビルドエラーを潰すループに入ったら手を止めて型定義を読む**
